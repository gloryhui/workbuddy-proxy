# Codex 高效开发与按风险验证规范

适用于本仓库的日常开发、专项验证及发布准备。来源：[Issue #5](https://github.com/gloryhui/workbuddy-proxy/issues/5)（2026-11-02 落地）。与 [AGENTS.md](../AGENTS.md) 配合使用，保留既有安全约束与强制 CI 门禁。

核心原则：先完成最小正确改动，再按风险验证；有证据就停止，无新变化不重复；未执行的检查不得声称通过。

以下命令从仓库根目录执行。历史发布清单中的授权仅属于其原会话和版本，不构成新任务的推送、合并或发布授权。设计任务另遵守 [Studio V2 设计交付与实现契约](studio_v2/DESIGN_SPEC.md)。

## 风险分级与最低充分验证（强制）

| 等级 | 典型变更 | 日常开发最低验证 | 额外验证触发 |
|---|---|---|---|
| **L0 文档** | Markdown、注释、纯说明文字 | 查看相关 diff、`git diff --check`，无代码变更不编译 | 生成器、脚本或链接有变时补相关检查 |
| **L1 纯 UI 视觉** | 颜色、圆角、padding、图标白边、布局，不变更状态/事件 | GPUI fmt + 增量 `cargo check`，在 GUI 可用时检查**受影响的画面** | 改字体度量、窄窗布局、共享组件时扩大到代表场景 |
| **L2 UI 交互** | 输入、焦点、弹窗、草稿、选择、主题/语言切换 | L1 + 相关单测 + 受影响交互的真实路径 | 持久化、原生窗口、进程生命周期升 L3 |
| **L3 核心/高风险** | Key、配置/数据库、代理协议、路由、同步、升级、原生进程或构建依赖 | 相关 Core/GPUI 单测、针对性集成和失败/回滚检查 | 影响平台、性能或包体积时增加对应实测 |
| **R 发布/专项** | RC、正式发布、安装/升级/回滚、明确要求全量验收 | 仓库要求的完整 CI、三平台产物以及必要发布门禁 | 不得用 L0–L3 的简化流程宣称“可以发布” |

分级取决于**真实影响面**，不取决于源文件所在目录。全局字体、主题 tokens、共享输入组件等可能升级验证范围。

特别例外：[#4 移除内嵌字体](https://github.com/gloryhui/workbuddy-proxy/issues/4) 是影响全局文字度量与发布包的专项，必须做同配置 Release 体积 A/B、Windows/macOS 中英文排版和相关主题/编译验证；但如果 Core 没改，不必在每次局部迭代中反复跑所有 Core Python 脚本。

## 每轮 Codex 的执行流程

1. **定位**：读取任务、`git status --short`、本轮 diff 和相关文件；优先 `rg` + 限定目录/行数，避免习惯性扫描整个仓库。
2. **定级**：内部判 L0/L1/L2/L3/R，最多三行说明“改动范围 + 本轮最低验证”。简单任务无需长计划。
3. **批量修改**：同类 UI、共用组件一次集中处理；禁止每调 1px 就重新编译/截图/基准测试/更新进度。
4. **验证**：先便宜、相关的检查，只有实际风险、错误或门禁要求才升级；失败后定位根因并定向重跑。
5. **交付**：审查 diff、`git diff --check`、确认实际执行的验证与未覆盖风险；结论优先，不复述全过程。

## Rust 编译和测试规则

从仓库根目录，按本次改动实际级别选命令：

```bash
# 日常 UI 轻量检查
cargo fmt --manifest-path gpui/Cargo.toml --check
cargo check --manifest-path gpui/Cargo.toml --locked

# UI 交互变动：使用真实存在的测试名/模块定向运行
cargo test --manifest-path gpui/Cargo.toml --locked <实际测试过滤器>

# Core 行为受到影响时
cargo test --locked <实际测试过滤器>

# 高风险或 PR 指定时，执行严格 Clippy
cargo clippy --manifest-path gpui/Cargo.toml --locked --all-targets -- -D warnings

# 只有包体/性能/正式发布/实际 GUI 包需求才进行 Release 构建
cargo build --manifest-path gpui/Cargo.toml --release --locked
```

- `<实际测试过滤器>` 是占位符，不可原样执行；先查现有测试名，无法安全缩小时执行相应完整测试集并说明原因。
- 不得每改一个文件就 `cargo build --release`、全量 `cargo test`、三平台打包或四轮基准。
- **复用**兼容的 `target/`、`gpui/target/` 和 `CARGO_TARGET_DIR` 缓存。禁止例行 `cargo clean`、每轮新建 target。不同 OS/工具链/feature 不兼容时才隔离，并说明。
- 同一 SHA 和参数已经成功的门禁检查应复用结果，不重复派发 CI。
- 不擅自调整/关闭强制 CI、删除测试、忽略失败，不能用这份文档规避发布质量。
- 性能改进必须基于真实前后测量；不能无数据声称节省了 X% 时间或 Token。

## GUI / Figma / 截图规则

- **只检查受影响组件、页面、状态**：单个按钮调整不回归全部 40 张画板；全局字体、主题、共享弹窗按影响面扩大。
- 一般视觉变动：优先一张当前系统的代表窗口截图；影响窄布局时再验证 1100×700；HiDPI/跨平台只有与风险相关或发布时全做。
- 普通迭代不生成几十张同样截图，不做无关的全帧 RGB/逐字形像素一致性检查。重点发现溢出、裁切、居中、焦点、可访问性、字体回退和真实交互故障。
- Windows 继续遵守既有 GDI/Pillow `ImageGrab` 优先规则；已知持续超时的截图通道不重复尝试。
- 环境无法执行真实 GUI、输入法、辅助技术或跨平台实测时标**未验证**，不得伪称通过或无限循环。
- benchmark、冷启动/RSS、长列表压力测试及安装升级验收仅在对应性能风险、专项或发布时运行。

## 禁止无意义的重复循环

- **同一候选无代码、配置、数据、环境改变，也没有新失败证据，禁止反复执行相同的耗时命令。**
- 失败：提取关键错误 → 判断源码/环境/偶发 → 最小修复 → **定向重跑**。偶发失败最多一次同条件重试用于判别，再失败就报告阻碍，禁止刷绿。
- 格式/构建测试通过后，如果对应输入未变，无需再次执行。
- 同一待验收候选完整回归、三平台构建、性能基准、整帧视觉审查原则上**各只执行一次**；修复影响范围时定向复验，必要时最终再做一次完整门禁。
- 不为补漂亮的 QA 报告而增加不需要的新框架、测试矩阵、脚本、性能轮次或文档版本。真正发现 bug 时可以补最小回归测试。

## Token / 上下文 / Agent 预算

- 简单任务直接做，不反复复述历史需求。复杂任务的计划和进度更新简短、只报实质性节点。
- 优先精确文件、`rg`、限定行号；历史 QA 和交接从 [固定版本快照](https://github.com/gloryhui/workbuddy-proxy/tree/v0.6.1/docs/studio_v2) 定向追溯，不把庞大时间线或 Cargo/CI 原始日志整体灌入上下文。
- **成功只报结论及必要计数；失败只报首个根因、关键上下文和少量日志尾部**。原始日志可留在本地或 CI Artifacts，不全文粘贴到对话。
- 默认**单 Agent**；独立并行能明显缩短关键路径时最多用 2 个子 Agent，避免重复读取、测试和汇报。
- 除用户另有要求，最终中文报告建议 **6–12 行**：改动、结果、已执行检查、未验证/风险、提交或 PR。禁逐命令流水账、同义反复。
- 文档/历史 QA 仅在里程碑、验收状态实质变化或用户明确要求时集中更新；不每改一个像素就刷新全量 `baseline_and_qa.md`、Figma 节点表或时间线。

## 临时资源、安全与既有规则

- **保留** `AGENTS.md` 中的 Codex 署名、路径安全、进程退出、所有权检查、临时资源安全清理、密钥保护和 Windows 截图规则。
- 不使用危险模糊清理命令；不删除非本次创建或归属不明的文件/目录，不删除编译缓存和用户数据。创建了临时数据库、隔离配置或 GUI 子进程就必须正常退出并安全清理。
- 清理汇报遵守以下规则（与 `AGENTS.md` 一致，只精简汇报冗余，不删安全清理步骤）：

> 每轮若实际创建过测试进程、临时数据库、配置或专用临时目录，仍须完成进程退出、归属核验及安全清理。正常清理在交付中用一句话概括；遇清理失败、遗留资源、磁盘空间异常或用户明确要求时，再详列路径、释放空间、保留项及磁盘剩余空间。未创建此类临时资源的文档/静态检查无需执行磁盘巡检或报告。

- 使用隔离数据与合成密钥，真实 API Key、账号、用户隐私不得进入日志和截图。

## 停止条件与交付边界

满足全部条件即结束本轮，不得因为“可以再测”无限扩大范围：

1. 用户要求的改动完成，无已知阻塞缺陷。
2. 对应级别必要检查通过，或客观环境限制已明确列出；不可伪造通过。
3. diff 仅含必要改动，残余风险、所需后续高阶检查清楚。

**任务完成不等于批准发布。** 未经授权不得 push、合并、修改 main、创建 Release。提交 PR 时关联 Issue，等待用户审核；强制 CI 失败不可忽略。
