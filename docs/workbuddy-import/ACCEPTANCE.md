# 严格验收矩阵 v1.0

验收结论只允许 PASS / FAIL / BLOCKED_EXTERNAL / NOT_RUN。不得把“代码看起来正确”“cargo check通过”“HTTP200”写成业务验收PASS。每条证据必须包含基线/构建commit、隔离目录、准确命令、退出码、关键断言值、日志路径；GUI还需事件步骤和截图。性能附原始测量和机器信息。下列预期来自冻结设计，不允许按实现输出反改预期。

## 用户确认的验收口径修订（2026-10-18）

以下修订来自用户本会话的明确业务要求，覆盖本文及旧报告中冲突的验收口径。用户已授权恢复 Goal，按本修订推进实现与验收；历史失败保留原始口径和结论。

- 历史 JSONL 全量回填是可中断、可续传的后台任务。软件启动、代理转发、页面操作和统计查询不等待历史回填完成；统计展示已提交入库的记录，并明确标示仍在导入或存在积压，不把部分结果伪报为完整历史。
- 用户追加要求：统计界面必须展示后台导入进度条和剩余数量，适用于机械硬盘等较慢机器。显示已入库记录数，并为剩余数量明确标注单位；不能把剩余文件数、字节数或待人工确认数写成剩余记录条数。扫描发现阶段总量未知时显示不定进度及“正在扫描”，不伪造百分比/剩余条数；实际暂停、读取失败、等待重试也须有对应状态，不能显示为已完成。
- 进度统计由后台维护，UI 状态轮询不得读取 JSONL 或触发重新扫描；进度条按已提交检查点而非重复读取累计量更新，重启后可恢复，并允许源追加/截断/替换导致已发现总量变化。显示“已发现数据”的范围，不能将尚未发现的文件算作0或在发现未结束时宣告100%。进度信息缺失、格式不支持时显示未知，不靠默认0伪报完成。用户已确认口径：进度条按已发现文件的已提交数据量计算，旁边显示剩余文件数与剩余数据量，另列已入库记录条数；不为取得精确剩余记录条数增加全量计数扫描。文件数和数据量只反映最近发现/检查点快照，扫描未结束时总量仍未知；追平后继续增量同步，不把待人工确认记录数当作未读文件积压。进度条已实现；真实检查点/API测试及原生回填、暂停、错误恢复的旧候选证据见 R09-20261018-NATIVE-AUDIT，并保留其核心哈希范围。当前bcaa/8f4配对及发现未知总量、完整核对不定进度已实际录制，见 R09-20261018-MAPPED-READER-NATIVE；当前候选ARM镜像的驻留全应用退出也已在实际百万回填时验证，证据见 R09-20261018-MAPPED-READER-PACKAGE-NATIVE；完整12阶段与百万status也已通过；百万续传和最终文档镜像的实际状态以 R09-20261017-CURRENT 为准，不由本契约预判。
- 取消“1GiB / 百万条历史记录必须在 600 秒内全部回填完成”的业务通过门槛。保留实际规模、用时、吞吐、CPU、内存、磁盘及 SQLite 等诊断数据，仍须证明任务持续推进、最终计数/Token/积分准确、来源去重和断点续传有效；不得缩小语料或将未完成回填计作完整验收通过。
- 后台回填期间仍须验证软件可用性：前台输入不被源文件 I/O 阻塞，代理转发延迟/事件完整性、查询延迟、资源有界、正常退出均遵守本文原有要求。后台线程本身不是“不影响软件”的充分证据；共享 SQLite writer 的竞争也必须实际验证。
- 保持固定 5 秒增量同步、页面刷新与同步独立，以及正常增量样本每次不超过 10 秒的原有门槛；覆盖其他文件存在历史积压时的已追平文件与新项目/新文件。尚未追平的巨型文件必须如实报告积压，不声称其尾部新增已实时统计。
- UI 按用户当前远程桌面的实际分辨率和缩放验收，记录实测显示与窗口尺寸；不以恢复本地物理显示器原分辨率、指定 1x/2x 环境作为本轮前置条件。三来源、中英文、交互与异常态检查保留，布局在当前桌面可实现的窗口尺寸范围内验证；无法呈现的精确宽度断点记录覆盖范围，不伪造截图或称已验证其他显示环境。

性能脚本与矩阵聚合器按本修订记录完整回填用时、回填中部分统计查询和检查点进度；操作观察窗口结束记录 INCOMPLETE_OPERATIONAL_WINDOW，不等于产品超时失败或完整阶段通过。完整12阶段必须对应同一候选哈希，当前进度见 R09-20261017-CURRENT；保留旧原始报告及其旧门槛范围，不能直接把旧 FAIL 改成新 PASS。

## 性能硬门槛（S10.03）

统一 release 构建、同机同数据、Mock上游、固定seed；先warm-up，再各跑3次取中位数并保留每次值。用内置 counters/测试I/O hook测量实际读取，不以日志缺失推断没有读取。测试hook只用于注入/计数，不能替换生产算法。

1. 规模：100,000 条至少128MiB，1,000,000 条至少1GiB，多文件（≥1000个）和单巨型文件两种；清楚标注实际字节数和消息数，不复制一条相同ID冒充百万唯一记录。
2. 增量：固定5秒后台调度。在release、无DB外部锁/退避、≤1000文件、单轮≤500条新增且≤8MiB的常态条件下，已追平文件的完整新行及新项目目录/新JSONL的小文件首批完整行，从源写入并flush完成至SQLite提交后可查询均≤10秒。分别记录源落盘、commit、查询可见的单调时钟时间；覆盖刚错过tick的相位，至少20次且每次达标，不以中位数掩盖超时。其他文件回填时已追平文件同样达标；巨型文件自身未追平、故障/休眠另报积压，不纳入正常样本。计时不从模型开始回答算，也不包含页面刷新等待。手动增量检查2秒内排队反馈，无其他扫描积压和外部锁时500条新增5秒内可查。
3. 资源：导入worker额外RSS峰值≤64MiB；从100k到1M规模额外峰值增长≤16MiB；不能把整个文件/所有候选放内存。测量使用完整同规模语料的无报表查询独立导入过程，以整个核心RSS作为worker的保守上界；另行如实报告并发报表查询过程的整个核心RSS，不能将reader缓存混称为worker RSS。
4. 首次回填：按上述用户修订，1GiB、1M条历史数据在后台逐步导入，不以10分钟内全部完成作为通过门槛。记录实际耗时与CPU/磁盘/SQLite分解，验证回填持续推进、部分统计可查、启动/前台/代理正常、增量正常和退出重启续传；最终完成时独立核对全量事实、账本及Token/积分。语料规模不缩减，观察窗到期但仍正常推进只记“未完成”，不能冒称完整规模验收通过。
5. 空闲：初始完成后5分钟内常规stat允许，未变文件正文读取=0（刻意安排full scan的轮次单独测）。worker CPU中位数<1%单核心，不持续忙轮询。
6. Proxy影响：同机4并发Mock流式请求，导入开/关各至少200个请求，P95首内容延迟增加≤max(10ms,基线P95的10%)；新增由导入导致的请求失败/事件丢失=0。队列有界、数据库锁注入单独测，不混入正常延迟门槛。
7. 查询：1M条索引数据，当天/30天 dashboard 和第一页明细每轮至少50次、共3轮，各轮P95≤500ms；查询预算超限时返回既有超时码，UI不阻塞。通过query plan证明来源索引使用，不能关闭超时。
8. UI事件处理不得执行源文件I/O；开启回填时点击来源按钮下一帧选中态可见，用户输入没有>100ms同步工作阻塞证据。
9. 停止：正常/导入中/排空巨行时进程在原4秒flush预算+1秒调度余量内退出；不能杀WorkBuddy或留孤儿导入线程。
