## 维护方式

1. 编辑 `release_plan.json`：保留每个任务的已有成果、剩余工作、验收标准与历史依据。完成实际批次后记录任务 `acceptance`、批次 `status`、`accepted_frames` 和本候选 `acceptance_evidence`，未实测不得改为 passed。
2. 同步 `figma_node_map.md`、`visual_review.json`、功能保护矩阵与 QA。每批写一个有完整范围的QA章节，不把多个像素调整拆成多个“新功能”。帧的已签收集合必须与计划 `accepted_frames` 相同。
3. 先提交本批代码、证据与QA，使生成器能从Git取得真实来源；随后一次刷新报告，例如：

   ```sh
   python3 scripts/update_studio_progress.py \
     --task 69 --status recorded \
     --goal-status active \
     --note 'B02模型与四协议6帧整批签收；剩余15帧，下一批B03'
   ```

   示例参数为B01签收后的实际状态；复跑时按最新Goal/QA调整。`--goal-status` 只记录面板状态，不恢复或暂停Goal本身。恢复施工后同时更新计划中的前置条件和当前批次。
4. 生成器核对40个节点的唯一归属、任务ID/历史依据、依赖无环、签收集合、passed批次的任务/依赖/证据，再生成 `release_plan.md`、HTML与报告JSON。任一校验失败都不生成“全绿”报告。检查后提交报告，再推送整个批次。

`release_plan.json` 是可编辑计划，`release_plan.md` 和 `progress_timeline.json` 为生成结果。不要手工改HTML内嵌JSON；生成器会覆盖它。HTML模板可修改，页内搜索/筛选/主题只用于查看，不会自行修改验收状态或访问远端服务。

## 签收口径

- **主体已实现/历史分项已验证**：代码与证据已经存在，不等于最新设计或最终发行包通过。
- **界面签收**：40帧按对应功能批次核对最新设计、实际交互、相关状态和两尺寸；R01统一检查共享状态与整套覆盖。不能把同一个全局门禁反复作为40张页面的独立施工任务。
- **正式版可发布**：界面签收和R01–R04的输入/无障碍、平台、性能、Core兼容、CI、签名/分发方式、安装升级回滚等门禁必须同时通过。40帧清零仍不自动代表可发布。

已有页面浏览器验证限制见 [浏览器记录](benchmarks/progress-timeline-browser-check.json)：工具明确拒绝 `file:` 并禁止替代服务器/浏览器/渲染器绕过。因此本次继续做源码、数据、JavaScript语法和离线逻辑校验；不宣称已实测浏览器像素、响应式渲染或主题观感。该限制不改变计划与实际验收状态。
