# 设计与性能边界

## 目标和取舍

项目定位是 WorkBuddy 的个人本机模型代理。用原生界面降低 UI 运行时开销，用单线程 I/O 调度器减少空闲线程，用连接复用减少握手，用限额避免输入和请求队列无界增长。没有绝对最小 RAM 或最高吞吐量承诺。

网络热路径只进行本地认证、有限 JSON 借用解析和会话哈希。请求体保留在一个引用计数 Bytes 中，交给上游；不重新序列化工具定义。响应通过流直接返回，不累积完整输出、不解释 SSE。HTTP 状态、Content-Type、Content-Encoding、Retry-After 保留。原始内容由上游产生，工具调用历史由 WorkBuddy 管理。

请求体仍需收集才能识别缺失的聊天会话头；这不是严格端到端输入零拷贝。8 MiB × 4 是逻辑输入预算，**不是进程 RSS 上限**：解析元数据、HTTP / TLS 缓冲、连接、系统框架和分配器另占内存。相同消息前缀和历史改写无法在没有客户端 ID 时完全消除歧义。

## 原生界面

Rust 调用一个小型 C / Objective-C 平台适配层。Windows 主线程运行 Win32 消息循环，Mac 主线程运行 AppKit 事件循环，后台只有一个 I/O 运行时。测试请求在原生工作线程中执行，保持设置窗口响应。UI 不通过 HTTP 获取配置，控制 API 只供单实例唤起和测试停止服务。

FFI 字符串所有权由 Rust 分配，平台读取后调用 `wb_free`。FFI 入口捕获 Rust panic，避免 panic 穿越 C 边界。密钥字段不会回填上游 Key。关闭设置窗口只隐藏窗口，托盘 / 菜单栏负责退出。

## 性能验证方式

`scripts/benchmark.py` 启动独立 mock 上游和独立代理子进程。测量 RSS 只针对代理 PID，原生 UI 与网络核心在同一 PID 时一起计入。Windows 使用 GetProcessMemoryInfo 的 WorkingSetSize，Unix 使用 ps RSS；这些指标存在平台差异，不能直接作为跨平台排行榜。

基准包含：预热 10 次；直接和代理各 200 个小请求，记录 p50 / p95；4 并发、80 个约 1 MiB 请求，每 150 ms 采样 RSS；负载结束后记录进程 RSS。小请求客户端每次重建连接，上游连接由代理复用。mock 禁止保存请求，测试数据不含真实 Key。

短暂峰值可能被采样遗漏；本地 HTTP 不覆盖 TLS 首次握手、真实 provider 速率限制或模型时间。benchmark 输出记录 OS、架构、模式、二进制大小和脚本参数。指标作为可复现实测，不作为实时互联网速度预测。代码或依赖变更后重新测量。

## 发布验证

GitHub Actions 在 Windows、Apple Silicon Mac、Intel Mac、Linux 上进行编译、lint、单元测试、执行实际二进制冒烟测试；Windows 另执行原生窗口模式。自动测试不代替用户在目标机上的人工 UI、WorkBuddy 真正对话和上游真实账号验收。

发布包仅含二进制、许可证、说明和 Windows 诊断启动器。用户配置始终在发布目录外。Git 忽略规则排除密钥文件、构建目录、日志和基准中间文件。
