## 交付内容

在原手动清除（`Writer::delete_finished`，`MaintenanceKind::Clear`）的分块删除循环里，**先落墓碑、再删明细**：

```sql
UPDATE workbuddy_import_ledger
   SET state = 'deleted_manual', request_id = NULL, updated_at_ms = updated_at_ms
 WHERE state = 'imported'
   AND request_id IN (SELECT request_id FROM usage_requests WHERE id IN (…))
```

紧随其后才是原有的 `DELETE FROM usage_requests WHERE id IN (…)`。

三条语义：

1. **顺序不可颠倒**：ledger 必须先离开 `imported`，否则删除事实行会触发 `ON DELETE SET NULL`，让 `state='imported'` 与 `request_id IS NULL` 同时成立，直接违反账本自身的 CHECK（S05.07/S06.03 已两次踩到同一约束）。
2. **重扫同消息不复活**：账本行保留为 `deleted_manual`，而去重键（`SHA256(域 + namespace + sessionId + messageId)`）使重扫命中同一 `entry_key`；`resolve_replay`（S06.03）对已存在行只做 no-op 或冲突判定，**任何路径都不会把墓碑改回 `imported`**。
3. **代理原清除语义不变**：墓碑 UPDATE 只作用于账本行，而代理事实行**没有账本行** —— 受影响的账本行数为 0；删除语句本身一行未改，`MaintenanceKind::Retention` 分支在本项**故意留空**（由 S07.02 接入），因此自动保留清理的行为此刻与改动前完全一致。

## 错误场景证据（真实失败）

`gate.txt` 之前有一轮真实失败：第二个用例把清除水位设成了**代理行**的 id，而夹具里代理行是先插入的（id 更小），于是水位覆盖不到导入行、`deleted` 为 0。修正为让导入行先插入并断言 `proxy_id > imported_id`，水位停在导入行上 —— 用例意图（只清除范围内的一行）保持不变，断言未放宽。
