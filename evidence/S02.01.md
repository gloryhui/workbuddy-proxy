## 验证方法

设计稿**只**在一次性数据库上验证（AC009 要求“禁止对真实库执行设计稿”）：

1. 用真实 release core 在隔离沙箱内生成 v6 数据库（`PRAGMA user_version=6`，对象清单已导出）。
2. 写入合成 v6 数据：1 个 run、3 条 usage_requests（`completed`+complete/upstream、`failed`+missing/none、`connection_test`+`in_flight`+not_applicable）、1 条 `priced` CNY 费用行。
3. 复制到临时文件，按 `store::apply_step` 的语义执行设计稿：**BEGIN 前 FK OFF**（`usage_costs.request_id` 对 `usage_requests` 有 `ON DELETE CASCADE`，FK 开启时 DROP 旧表会级联删除费用行）、单事务执行脚本、`foreign_key_check`、`integrity_check`。
4. 逐项核对列/约束/视图/触发器/索引/设置列，并对新约束做负例注入。

### 追加（S02.02 期间发现的偏离，已修正并重验）

接入 `store.rs` 后，4 个既有回归测试（`startup_repair_settles_abandoned_costs_from_their_own_snapshot`、`a_failed_repair_is_queued_before_the_scan_advances`、`a_large_legacy_backlog_is_fully_repaired_at_startup`、`a_large_legacy_repair_finishes_through_the_real_writer`）失败，报错为 `record_origin` 互斥 CHECK 的 proxy 分支不满足。根因：设计稿把 `upstream_protocol` 从 v6 的 `TEXT NOT NULL DEFAULT 'openai_chat'` 改成可空且**无默认值**，任何省略该列的插入都会得到 NULL，从而违反 proxy 分支的 `upstream_protocol IS NOT NULL`。生产插入路径（`store.rs:725`）显式提供该列，因此只有依赖 v6 默认值的既有测试受影响。

按 DATA-API §3「设计稿与实现不一致时必须修正并重跑验证」，`0007.sql` 恢复 v6 默认值：`upstream_protocol TEXT DEFAULT 'openai_chat' CHECK(...)`。导入行按 §3.1 必须**显式传 NULL**（否则会拿到默认值并违反 import 分支），proxy 行仍要求非空。该偏离已写入 `0007.sql` 头部注释，正文因此**不再与设计稿逐字节相同**（唯一差异就是这一列定义）；探针改为直接验证实际迁移文件 `src/stats/migrations/0007.sql`，并新增断言 `upstream_protocol keeps the v6 default`。

重验结果：`dist/workbuddy-import-validation/S02.01/migration-0007-run.txt`，**problems=0 / probe_exit=0**（45+1 项断言全部 PASS，含合法导入行显式传 NULL 被接受、proxy 行缺 `run_id` 与 import 行带 `http_status` 被拒、无主费用行被 FK 拒绝、导入行费用被触发器拒绝）。`docs/workbuddy-import/schema-v7.sql` 作为冻结设计稿**未被修改**（该文件不在任何任务的允许列表内），偏离只体现在生产迁移与证据中。
