## 交付内容

| 项 | 内容 |
|---|---|
| `MappingPreview` | `mapping_id`/`classification`/`requested_model`/区间/**`watermark_rowid`**/**`mapping_revision`**/`affected_count`/`token`/`expires_at_ms` |
| `MAPPING_TOKEN_TTL_MS` | `15 分钟` |
| `preview_mapping(tx, mapping_id, from_ms, to_ms, now_ms)` | 冻结该模型与区间内 `pending_classification` 行的**最高 rowid** 与规则 revision；token = `SHA256(域 + mapping_id + 水位 + revision + 区间)`（64 hex），因此预览无法被重放到另一批行或更新的规则上 |
| `MappingTaskRejection` | `TokenExpired` / `TokenAlreadyUsed` / `RevisionConflict` / `ProxyIntervalProtected`，错误码分别为 `stale_batch`/`stale_batch`/`mapping_conflict`/`mapping_conflict` |
| `claim_mapping_task(tx, preview, now_ms)` | 四类拒绝按序检查，**拒绝时零写入**；通过则把规则置为 `running` 并记录冻结水位 |
| `revoke_mapping_rows(tx, mapping_id, limit)` | 分批撤回该规则产出的 `imported` 行：**先**把 ledger 改回 `pending_classification` 并清空 `request_id`，**再**删除对应事实行 |

关键语义：

- **过期/重复 token**：`now_ms > expires_at_ms` → 过期；token 与冻结内容不符 → 已用；规则已完成且 `reconcile_watermark >= 冻结水位` → 已用。水位为 0（预览没冻结任何行）时不算"已用"，因为新规则本来就从 0 开始。
- **冲突 revision**：规则 revision 与预览不符 → 拒绝（规则被撤销/改动过）。
- **规则不得覆盖已知代理区间**：`direct` 规则若与任何 `verified` 的 `proxy` 区间重叠 → 拒绝，绝不覆盖。
- **tombstone 不复活**：撤销只取 `state='imported'` 的行，`deleted_manual`/`deleted_retention` 完全不参与。
- **撤销只影响 workbuddy 行**：事实行的删除带 `record_origin IN ('workbuddy_builtin','workbuddy_custom')` 谓词；`proxy` 行与其事实行原样保留。

## AC039 覆盖

| 要求 | 用例与断言 |
|---|---|
| 预览冻结水位与 revision | `a_preview_freezes_the_watermark_and_the_revision`（`affected_count=2`、`watermark_rowid>0`、`revision=1`、token 64 hex、TTL 正确；之后新增的行**不**进入旧预览） |

| tombstone 不复活 | 同一用例断言 `deleted_manual` 行仍为 `deleted_manual` |

## 错误场景证据（真实失败）

`gate.txt` 之前有六轮失败，其中**两个是真实实现缺陷**：

1. **撤销删不掉事实行**：删除谓词写成 `record_origin = 'workbuddy'`，而该列只允许 `proxy`/`workbuddy_builtin`/`workbuddy_custom` → 事实行残留（测试测出 `facts=3` 而非 1）。修正为 `record_origin IN ('workbuddy_builtin','workbuddy_custom')`。
2. **`ON DELETE SET NULL` 与 ledger CHECK 冲突**：先删事实行会让 `request_id` 变 NULL 而行仍为 `imported`，直接违反 `CHECK(state='imported' ⟺ request_id=entry_key)`。修正为**先撤 ledger 再删事实行**。

其余四轮为夹具/编辑问题：`StoreError` 含 `rusqlite::Error` 无法 `PartialEq`（改用 `matches!`）；一次正则批量替换误伤了非目标断言并把 `pub fn route` 拆开，逐处修复；测试夹具的 `session_hash`/`message_hash` 对所有行相同触发 UNIQUE；重叠夹具两个区间都是 `verified` 而被 schema 拒绝（改为 `prepared`，正是被保护检查拦截的对象）；导入事实行必须显式传 `upstream_protocol = NULL`（该列有 `DEFAULT 'openai_chat'`，S02.02 已记录的偏差）；proxy 事实行需要先有 `stats_runs` 行。
