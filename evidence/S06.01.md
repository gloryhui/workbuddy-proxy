## 交付内容

| 项 | 内容 |
|---|---|
| `IMPORT_CHANNEL_CAPACITY` | **2**（专用容量：一个正在交接、一个排队） |
| `MAX_PENDING_ACK` | **1**（最多一个待 ACK 批次） |
| `ImportMessage` | `Tick { at_ms }` / `Shutdown` |
| `ImportChannel` | `bounded()`、`offer()`（**`try_send`，绝不阻塞**）、`sender()`、`take_receiver()` |
| `OfferOutcome` | `Accepted` / **`Busy`**（满则退让）/ `Closed`（worker 已退出） |
| `AckWindow` | `begin(batch)` / `ack(batch)` / `pending()` / `is_free()`；`AckOutcome` = `Opened` / **`Busy`** / `Mismatch` / `Idle` |
| `ImportState` | `disabled` / `idle` / `discovering` / `backfilling` / `scanning` / `paused` / `degraded`，含 `as_str`/`parse`/`is_active` |

**AC041 的实现要点**：

1. **队列满只让 worker 退让**：`offer` 走 `SyncSender::try_send`，满时立即返回 `Busy` —— 调用方**没有等待路径**，等待的只能是消费端。测试用 `Instant` 实测"第三次投递在 50 ms 内返回"，证明不存在阻塞。
2. **Proxy begin/finish 不阻塞**：转发路径拿到的是 `sender()` 克隆，而克隆**共享同一容量上界**（自检中直接断言克隆句柄在满队列时同样得到 `Full`），因此转发路径既不能等待、也不能在 worker 背后另建无界队列。
3. **不挤原事件队列**：通道是本模块自有的 `sync_channel`，与代理的事件队列完全分离。
4. **最多一个待 ACK 批次**：`AckWindow::begin` 在已有待 ACK 时返回 `Busy`，错误批次号的 ACK 返回 `Mismatch` 且**不**释放窗口 —— 两个 writer 不可能同时压在同一检查点上。
5. **没有"实时"模式**：`ImportState::parse("realtime")` 与 `parse("syncing")` 均为 `None`（测试断言），状态集恰 7 个、活动态恰 3 个。

## 错误场景证据（真实失败）

`gate.txt` 之前有一轮真实失败：clippy 报 `ImportChannel::sender` 与 `AckWindow::pending` 在生产路径无使用点。按既定规则**不加抑制**，改为在启动自检中真实调用 —— 并用克隆发送端做了一次"共享容量上界"的断言（比单纯消除 dead_code 更有价值）。6 个新用例随后一次通过。

## 结论

PASS（AC041 满足：容量 2 的专用通道满时只让消费端退让、投递端零等待；克隆发送端共享同一上界，转发路径的 begin/finish 不可能被导入阻塞；最多一个待 ACK 批次；运行状态机闭合且没有实时模式）。本项只建立通道与状态，不启动线程、不写库。
