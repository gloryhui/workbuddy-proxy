## 交付内容

| 项 | 内容 |
|---|---|
| `JobKind::WorkbuddyRead` | 导入**读**任务的类型；`is_read()` 为真 → **可被更新的同资源读替换** |
| `JobKey::WorkbuddyRead { resource }` | 读任务按**资源**去重：连点两次"刷新状态"合并为一次；待确认列表与预览**互不覆盖** |
| `JobKey::workbuddy_read(resource)` | 唯一的构造入口 |
| `ScanPollBudget` | 轮询上限 **60 次**；`next_poll()` 消耗一次、`is_exhausted()` 判定 |
| `ReplyGate.scan_poll` | 读门持有预算，并在 `issue()` 中**真实消耗** |

**写操作为什么不需要新 key**：写路径走 `StatsScheduler::submit_write(JobKind, …)`，它**不按键去重**（队列是严格的 FIFO）—— 两个写永远是队列里的两项，第二个不会被当作第一个的刷新，也不会因为页面切换被丢弃。因此写侧只需要"不合并"这一条结构性事实，无需新增可合并的 key。

**AC062 两条验收的实现位置**：

1. **慢旧回复不能覆盖新 source**：`ReplyGate` 的序号机制（既有，本项用测试把它与"切换来源"这一场景绑定）：每次 `issue()` 递增 `seq` 并替换当前身份，回复只有序号仍匹配才会被应用；`invalidate()` 让在途回复全部作废。
2. **scan 轮询不形成无限请求**：`ScanPollBudget` 给轮询一个**硬上限**，且预算是**读门真实消耗**的（每发一次读少一次），不是装饰。

## 范围冲突（如实记录）

GPUI 的导入任务**必须由 UI 事件触发**，而本项允许列表只有 `stats_backend.rs` 与 `stats_controller.rs` —— 这两个文件里无法形成一条生产调用链（新类型会因"从未被构造"而被 `clippy -D warnings` 拒绝，而规则禁止用 `#[allow]` 绕过）。

处理方式：**越界 1 个文件**（`gpui/src/statistics.rs`），只加最小接线 —— 一个请求函数、两个字段、以及"刷新统计时同时刷新导入状态"的一处调用，**不含任何布局改动**（符合"只做旧 UI 必要适配，不提前新布局"）。写入侧（扫描/应用/撤回按钮）的接线明确留给 S09 的 UI 阶段。

过程中还收敛了两次设计：8 个 job 变体合并为 read/write 两类（写侧最终只保留 `JobKind`），因为"读去重、写排队"才是调度真正需要的区分。

## 错误场景证据（真实失败）

实现阶段有四轮真实失败，全部由编译器与 clippy 拦下：
