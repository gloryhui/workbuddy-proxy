### 窗口层证据（第 2 次尝试的最终结论）

用 Swift + CoreGraphics 直接查询窗口服务器（`dist/workbuddy-import-validation/S09.08/winlist.swift`，只读，未安装任何东西）：

```
$ swift winlist.swift
id=20947 onscreen=false layer=0 alpha=1.0 bounds=["Height": 500, "X": 0, "Width": 500, "Y": 580]
id=20946 onscreen=true  layer=0 alpha=1.0 bounds=["Height": 901, "X": 240, "Width": 1440, "Y": 71]
total=2
```

**主窗口是 `onscreen=true` 的**（1440×901，位于 240,71），`alpha=1.0`，`layer=0` —— 也就是说窗口服务器认为它就在屏幕上。但按窗口 ID 直接抓图：

```
$ screencapture -x -l 20946 /tmp/win.png
could not create image from window
[exit=1]        # 文件未生成
```

而同一时刻的全屏截图，**md5 与截图矩阵里的 `zh-wide-all.png` 逐字节相同**（`ff6e9dcb13f736f57db77cda28f54774`）—— 两者拍的是同一张桌面。

**结论**：GPUI 的窗口在窗口服务器中**已注册且标记为在屏**，但**没有提交任何可捕获的图层内容**。这解释了两轮尝试里的全部现象：窗口计数从 0 变成 1、`frontmost` 能设成 true、脚本能"成功"产出 12 个 PNG —— 但**没有任何一张能拍到界面**，因为窗口本身没有可拍的内容。这是**环境/渲染层**的问题，与本次实现无关。

**因此 S09.08 保持 BLOCKED_EXTERNAL**，并且现在的阻塞描述比第 1 次精确得多：不是"窗口不存在"，而是"**窗口存在且在屏，但没有可捕获的内容**"。

**可继续的方向**（都需要环境或权限，非代码改动）：检查 GPUI 在本机是否因缺少某项系统权限/图形上下文而未提交图层；或在另一台机器上运行同一脚本。


### 根因：本机处于远程桌面会话，Metal 图层不提交到窗口服务器

前两轮把现象从"窗口不存在"推进到"窗口在屏但不可捕获"，本轮找到了**解释这一切的原因**。

**证据链**：

1. GPUI 链接了 **Metal** 与 QuartzCore（`otool -L`），即界面走 GPU 渲染：
   ```
   /System/Library/Frameworks/Metal.framework/Versions/A/Metal
   /System/Library/Frameworks/QuartzCore.framework/Versions/A/QuartzCore
   ```
2. **本机是远程会话**：`com.apple.RemoteManagementAgent`（PID 840）处于运行状态，前台进程里同时有 **AweSun、RustDesk、O+Connect** 三个远程桌面客户端。
3. 硬件本身没有问题：**Apple M4**、**Metal 3**、1920×1080 在线。
4. **backing scale = 1**（屏幕 1920×1080，窗口 1440×901），因此逻辑点与物理像素相同 —— `-R 240,71,1440,901` **本应正好框住窗口**，实测该区域却是桌面。
5. 触发三次 resize（强制重绘）后，`screencapture -l <window id>` 仍然返回 `could not create image from window`（exit 1，文件未生成）。

**结论**：在远程桌面会话下，这个 Metal 渲染的窗口**在窗口服务器中注册、标记为在屏、`alpha=1.0`，但它的图层内容不提交给窗口服务器**，因此任何截图途径（按窗口 ID 或按屏幕区域）都拿不到界面。窗口计数、`frontmost`、脚本的"成功"产出，都不足以证明界面真的被画出来了 —— 这正是 AC072 强调"截图不能替代实际数据断言"的另一面：**反过来，数据断言也不能替代截图**。

**这不是实现缺陷**，也不是脚本缺陷：同一份脚本在本机产出了 12 个文件、22 条断言全绿，唯独画面是桌面。**在本地物理会话（非远程桌面）下应当可以正常截图**。

**S09.08 保持 BLOCKED_EXTERNAL。** 解除条件已经非常明确：**在本地物理会话中运行 `scripts/workbuddy_import_ui_test.py`**（脚本已就绪，不需要任何代码改动），或提供一台可截图的机器。


### 对照实验：证实"只有 Metal 窗口不可见"

远程会话的假设需要一个对照，否则"截图看不到 GPUI"也可能只是本机截图链路整体坏了。用一个**非 Metal** 的窗口做对照（TextEdit 新建文档，同样由 System Events 确认窗口数为 1）：

| 对象 | 全屏截图 md5 | 与桌面基线比较 | 结论 |
|---|---|---|---|
| 桌面基线（无窗口） | `ff6e9dcb13f736f57db77cda28f54774` | — | — |
| **TextEdit**（非 Metal） | `f3b2d0a4372654ab8d1dfa212f1946fa` | **不同** | **窗口可见** |
| **GPUI**（Metal） | `ff6e9dcb13f736f57db77cda28f54774` | **逐字节相同** | **窗口不可见** |

**这个对照排除了三种可能**：

- ✗ **不是权限问题** —— 同一时刻、同一权限下，TextEdit 的窗口被拍到了。
- ✗ **不是脚本问题** —— 两者用的是同一条 `screencapture` 调用路径。
- ✗ **不是"窗口不存在"** —— GPUI 窗口在窗口服务器里 `onscreen=true`、`alpha=1.0`、尺寸 1440×901 都正确。

**剩下唯一相符的解释就是远程会话下 Metal 图层不提交**。这也是本轮把根因从推测变成结论的依据。

（附带记录：对 TextEdit 按窗口 ID 抓取同样返回 `could not create image from window`，说明 `screencapture -l` 在**本会话下对任何窗口都不可用**，与 Metal 无关；真正能区分两者的是**全屏截图**，因此对照用的是它。）
