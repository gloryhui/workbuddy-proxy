## WB-RT-001 落地

公平遍历运行在 S04.01 已固定的 [`SYNC_INTERVAL`] = **5 秒**节奏之内：调度器**不接受任何设置参数**，模块内不出现任何刷新选项符号，`plan()` 每被调用一次就是一个 5 秒片。固定节奏与公平窗口是两个独立维度：前者决定"多久跑一次"，后者决定"一次跑多少"。

## 交付内容

| 项 | 内容 |
|---|---|
| `PER_FILE_BYTES` | `8 MiB`：单文件单片读取上限 |
| `PER_FILE_TIME` | `50 ms`：单文件单片耗时上限（与字节数**任一达限即让出**） |
| `ACTIVE_WINDOW` | `32`：单片最多参与的文件数 |
| `TurnResult` | `bytes`/`elapsed`/`has_backlog`；`exhausted()` 判定两个预算（达限即让出，预算是上限不是目标） |
| `FairScheduler` | `plan(files)` 产出本片顺序；`record(path, result)` 更新"谁还落后"；`backlog_len()` 供观测 |

两条公平规则：

1. **已追平文件的增量优先**：`plan` 先列出不在 backlog 中的文件（它们只有少量新追加，延迟敏感），再列 backlog 中的文件。因此**回填其他文件时，已追平文件的增量不会饥饿**。
2. **回填本身轮转推进**：backlog 内部按 `rotation` 起点轮转，每片起点 +1，一个完整周期等于 backlog 长度。因此**一个持续追加的大文件不会永久饿死其他文件**——它每片都会出现，但每片也都会让出（8 MiB / 50 ms），其余文件始终在片内。

单片文件数受 `ACTIVE_WINDOW` 限制；窗口外的文件在后续片继续参与（`plan` 每片都从最新发现结果重新构造）。

## 错误场景证据（真实失败）

`gate.txt` 之前有两轮真实失败：

1. `E0000`/解析错误：启动自检最初把 struct literal 直接写在 `if` 条件里（`if !TurnResult { … }.exhausted()`），Rust 不允许 → 先绑定为 `by_bytes`/`by_time`/`within` 三个局部变量再断言。
2. `the_backlog_rotation_moves_every_slice` 失败：我把"回到首片顺序"的断言放在了第 3 片，但 3 个文件的旋转周期是 **3 片**（start = 0,1,2），第 3 片是 `start=2` 的顺序，第 **4** 片才回到 `start=0`。修正为断言"三片互不相同 + 第 4 片回到首片"，与实现的轮转语义一致；实现未改。

## 结论

PASS（AC029 满足：持续追加的大文件在 10 个连续片中都未能独占——每片都包含其余文件；回填期间已追平文件的增量排在其之前；每文件受 8 MiB / 50 ms 双预算约束；单片文件数受 32 的窗口限制）。本项只做调度规划，不读文件内容、不写库、不启动线程。
