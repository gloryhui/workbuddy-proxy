## 交付内容

| 项 | 内容 |
|---|---|
| `ImportCounts` | `imported` / `excluded_proxy` / `excluded_retention` / `pending_classification` / `conflict` / `deleted_manual` / `deleted_retention` / `files_seen` / `files_pending` / `bytes_processed`；`total()`、`unresolved()`（pending + conflict） |
| `ImportStatusSnapshot` | `state` + `counts` + `last_incremental_at_ms` + `last_full_scan_at_ms` + `last_error_code` |
| `is_complete()` | **仅当**无未解决错误、`unresolved()==0`、`files_pending==0` 且状态非活动时为真 |
| `is_idle_with_work_left()` | 空闲但仍有活：`Idle` 且不完整 |
| `load_import_counts(tx)`（store） | 全部来自查询：ledger 按 state `GROUP BY`、`COUNT(*)` 文件数、`committed_offset < observed_size OR last_error_code IS NOT NULL` 的待处理文件数、`SUM(committed_offset)` 字节数 |

两条 AC044 的实现要点：

1. **restart 后累计数可信**：`ImportCounts` **没有任何内存累加器**，每个字段都是一次查询的结果。测试在同一进程内关闭连接、重新打开数据库后断言快照**逐字段相等**。
2. **错误文件未处理时状态仍需处理**：`is_complete()` 同时要求 `last_error_code.is_none()`、`files_pending == 0`（含"仍有未读字节"与"有未解决错误"两种文件）与 `unresolved() == 0`。因此 worker 空闲时也不会把"还有文件没处理完"呈现为"全部同步完成"—— `is_idle_with_work_left()` 专门表达这个状态。

| 未解决行阻塞完成 | `unresolved_rows_keep_the_snapshot_incomplete`（`pending_classification=1` 或 `conflict=1` → 不完整） |
| 结算态与总数 | `a_settled_snapshot_is_complete_and_the_totals_add_up`（无错误、无待办 → 完整；`total()=2`、`unresolved()=0`；空计数为合法零） |

## 错误场景证据（真实失败）

`gate.txt` 之前有一轮真实失败：clippy 报新类型在生产路径无使用点（`ImportCounts`/`ImportStatusSnapshot` 及其方法、`load_import_counts`）。按既定规则**不加抑制**，改为在启动自检中真实构造快照并断言三类判定（活动态不完整、错误态不完整、结算态完整），同时把 `load_import_counts` 接在自检已写入的行上。6 个新用例随后一次通过。
